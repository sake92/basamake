# SemanticDB Comparison Report: Our Extractor vs Scala 3 Compiler

Generated by comparing `ScalaDefinitionsExtractor` output against real SemanticDB
output from `scala-cli --semanticdb` (Scala 3.7.1).

## Methodology

1. Created 21 test `.scala` files in `/tmp/semanticdb_compare_*`
2. Compiled each with `scala-cli --semanticdb --semanticdb-target-root`
3. Parsed `.semanticdb` protobuf files to extract non-local symbols
4. Compared against our test expectations in `ScalaDefinitionsExtractorTest`

Legend:
- 🟢 = our implementation matches compiler
- 🔴 = our implementation differs from compiler
- 🟡 = out of scope (documented as "Not covered")

---

## Differences

### 🔴 1. `package.scala` wrapper name is `package$package.`, not `package.`

**Compiler output (package.scala)**:
```
com/example/package$package.helper().
com/example/package$package.default.
com/example/package$package.               <-- wrapper object emitted as symbol
```

**Our test C.18 expects**:
```
com/example/package.helper().
com/example/package.default.
```

The real Scala 3 compiler uses `package$package.` as the wrapper name for
`package.scala` files, NOT `package.`. This is a **spec bug in the plan**.

---

### 🔴 2. Trait constructors are emitted by the compiler

**Compiler output (c05_trait_obj_class)**:
```
com/example/T#`<init>`().
```

**Our test C.5 does NOT include** `T#`<init>`().` — the plan says "no constructor
for traits". But the compiler emits a synthetic constructor for traits.

---

### 🔴 3. `$package.` wrapper object is emitted as a separate symbol

**Compiler output (Foo.scala)**:
```
com/example/Foo$package.                    <-- OBJECT symbol for wrapper
com/example/Foo$package.topLevelMethod().
```

**Our code**: Does NOT emit the wrapper object as a separate `SymbolDefinition`.
The plan says "wrapper is owner-only" — but the real compiler emits it.

Impact: `go-to-definition` on the wrapper name would miss in our implementation,
but no user code references `X$package` directly (it's synthetic).

---

### 🔴 4. Top-level wrapping applies to ALL non-empty filenames

When our test uses `filename=""`, we disable wrapping. But the compiler ALWAYS
uses the actual `.scala` filename. Every file gets `X$package.` wrapping.

Example: `c11_type_aliases.scala` with `package com.example; type IntList = ...`:
- **Compiler**: `com/example/c11_type_aliases$package.IntList#`
- **Our test C.11** (filename=""): `com/example/IntList#`

This is by design in our tests (filename="" is a test-only artifact), but it
means our test expectations for C.1–C.16 don't match any real compiler output.

---

### 🔴 5. Case class user-defined `apply`: compiler puts under CLASS, not companion

**Compiler output (c16_case_class_user)**:
```
com/example/Person#apply().                <-- user apply under CLASS
com/example/Person#copy().                 <-- user copy under CLASS
```

**Our test C.16 expects**:
```
com/example/Person.apply().                <-- synthetic apply under companion
com/example/Person.apply(+1).             <-- user apply under companion (WRONG)
com/example/Person#copy().                 <-- synthetic copy under class
com/example/Person#copy(+1).              <-- user copy under class
```

The compiler puts the user-defined `apply()` and `copy()` under the CLASS scope
(`Person#apply()`, `Person#copy()`). Our plan says `apply` goes under companion and
`copy` goes under class. **Both are wrong** per the compiler — user-defined members
of the class body stay under the class.

The synthetic `apply` from the companion is a separate method:
`com/example/Person.apply().(name)` (with parameter). The user-defined `def apply(): Int`
is `com/example/Person#apply().` — distinct scopes, no collision.

---

### 🔴 6. Local classes/objects inside method bodies use `local<N>` symbols

**Compiler output (c07_method_body)**:
```
pkg/c07_method_body$package.top().         <-- method
pkg/c07_method_body$package.               <-- wrapper
local0                                      <-- class InMethod
local2                                      <-- object AlsoInMethod
```

**Our test C.7 expects** global symbols:
```
pkg/top().InMethod#
pkg/top().InMethod#`<init>().
pkg/top().AlsoInMethod.
```

The compiler uses `local<N>` for definitions inside method bodies. Our test
expects global symbols which is **incorrect**. Per `agents/semanticdb.md`,
locals are explicitly "Not covered".

## Out-of-Scope (documented as "Not covered")

### 🟡 Enum synthetic methods
Compiler emits: `$values`, `values()`, `valueOf()`, `$new()`, `fromOrdinal()`.
Our code: only emits enum class, companion, constructor, and enum case values.
✅ Per plan.

### 🟡 Case class synthetic members
Compiler emits: field accessors (`#name.`), `copy$default$N()`, `_1()`,
`unapply()`, `toString()`, product methods.
Our code: only emits companion, `apply`, `copy`.
✅ Per plan.

### 🟡 Method/constructor parameters
Compiler emits: `C#m().(x)`, `C#`<init>`().(name)`, `Show#show().(t)`.
Our code: skips parameters.
✅ Per plan.

### 🟡 Type parameters
Compiler emits: `Show#[T]`.
Our code: skips type parameters.
✅ Per plan.

### 🟡 Constructor parameter field accessors
Compiler emits: `C#x.`, `Person#name.`.
Our code: skips these.
✅ Per plan.

## What Matches Correctly

🟢 Basic symbol structure: `package/Class#`, `package/Object.`, `Class#method().`
🟢 Overload disambiguators: `()`, `(+1)`, `(+2)` — matches compiler exactly
🟢 Constructor symbols: `<init>().`, `<init>(+1).`
🟢 Backtick escaping: `` `+` ``, `` `==` ``, `` `unary_!` ``
🟢 Package prefix: `a/b/c/` for nested packages
🟢 Package object structure: `<pkg>/<name>/package.`
🟢 Enum class + companion + cases
🟢 Given definitions
🟢 Extension methods
🟢 Type aliases (including opaque)
🟢 Case class synthetics: companion, apply(), copy()
🟢 Wrapper for `Foo.scala`-style top-level defs: `Foo$package.method().`
🟢 `_empty_/` for empty package

## Recommended Fixes

### Must-fix (produce incorrect symbols):
1. **`package.scala` wrapper**: change `package.` → `package$package.`
2. **Trait constructors**: emit `<init>()` for traits
3. **Case class user `apply`**: keep under class scope (`Person#apply()`), NOT companion

### Should-fix (test expectations wrong):
4. **C.7 test**: locals inside method bodies should be skipped (or use `local<N>`)
5. **C.16 test**: `Person.apply(+1)` should be `Person#apply()` (user apply under class)
6. **C.18 test**: expected `package.` should be `package$package.`
7. **C.5 test**: add `T#`<init>`().` for trait constructor

### Optional (nice-to-have):
8. Emit `$package.` wrapper object as separate symbol
9. Emit field accessors for constructor parameters
